# 20 — アリーナより長く使うデータ: プールと寿命

> 🌐 [English](../20-beyond-arenas.md) · **日本語**

第5章と第8章では、同じ寿命を持つデータに `arena` を使いました。Web リクエスト、ゲームの1フレーム、コンパイルの1パスなど、1つの処理フェーズで使うデータを確保し、フェーズが終わるとまとめて解放できます。

しかし、データが単一のフェーズよりも長生きし、さらに**その寿命が予測不可能なとき**はどうすればよいでしょうか？

マルチプレイヤーゲームのサーバーでは、プレイヤーがそれぞれのタイミングで参加・退出します。フレームごとの `arena` では、プレイヤーのデータを必要な期間まで保持できません。一方、サーバー全体の寿命を持つ arena で参加のたびにレコードを確保すると、退出後もその領域が残ります。固定容量のプールなら、同じスロットを再利用して増加を防げます。

GC のある言語なら `Player` オブジェクトを作り、切断後の回収を GC に任せる方法があります。ここでは、**データプール**と**世代付きインデックス**で、確保済みの領域を明示的に再利用します。

## プール

プールは、あらかじめ確保した列の各スロットを再利用する仕組みです。第 [11](11-data-oriented.md) 章の `soa<T>` と同じく、フィールドごとに列を持ちます。ここでは `main` が配列を所有し、サーバーの実行中は保持します。すべての利用が終わるまで続く arena なら、そこにプールや `soa<T>` を置くこともできます。大切なのは、プールか arena かという区別ではなく、確保済みの領域を再利用するか、確保を繰り返すかの違いです。

1スロットを1行とし、使用中かどうかは `bool` の列で管理します。ハンドラは `borrow mut` パラメータを通じて、呼び出し元の列を更新できます。以下の断片は `main` 内に書きます。トップレベルの `:=` はコンパイル時定数の宣言になります。

```align
mut alive := [false, false, false, false].to_array()
mut hp    := [0, 0, 0, 0].to_array()
```

プレイヤーが参加したら、最初の空きスロット — `alive[i] == false` — を探し（またはフリーリストを使って `O(1)` で空きを見つけ）、すべてのカラムの行 `i` にデータを書き込んで、そのインデックス（`i64`）を返します。プレイヤーが退出したら、`alive[i]` を `false` に戻すだけです。

プールを確保した後は、参加・退出のたびに OS のアロケータを呼ばず、既存の配列を更新します。

## 再利用したスロットを古いインデックスが指す問題

`i64` のインデックスだけでは、そのスロットの利用者が入れ替わったことを区別できません。
1. アリス（Alice）が参加し、`id = 2` が割り当てられます。
2. ボブ（Bob: アリスの仲間）は、後で彼女を回復するために `target = 2` を保存します。
3. アリスが切断します。スロット2は空きになります。
4. チャーリー（Charlie）が参加し、空いたばかりの `id = 2` が割り当てられます。
5. ボブが `target = 2` に対して回復魔法をかけます。アリスの代わりにチャーリーが回復してしまいます！

これは [ABA 問題](https://en.wikipedia.org/wiki/ABA_problem) の一種です。保存したインデックスは同じスロットを指していますが、そこに入っているプレイヤーは変わっています。

## 世代付きインデックス

インデックスと**世代カウンター**の両方を持つ「チケット」を渡すと、この入れ替わりを検出できます。

```align
Entity { index: i64, generation: i64 }
```

プールには各スロットの世代を追跡するカラムを1本追加し、チケットが今も有効かを確かめる検査を書きます：

```align
mut generation := [1, 1, 1, 1].to_array()
```

```align
fn is_live(alive: slice<bool>, generation: slice<i64>, e: Entity) -> bool {
    if e.index < 0 { return false }
    if e.index >= alive.len() { return false }
    if e.index >= generation.len() { return false }
    return alive[e.index] && generation[e.index] == e.generation
}
```

どちらの列も、読む前にインデックスを検査します。範囲外のチケットは無効なので、配列の範囲検査で異常終了するのではなく `false` を返します。プールの各列を同じ容量に保つことと、そのプールが発行したチケットだけを使うことも必要です。

同じ参加・退出を、世代付きインデックスで追ってみます。
1. アリスが参加。スロット2は世代1。アリスには `Entity { index: 2, generation: 1 }` が渡されます。
2. ボブは `target = Entity { index: 2, generation: 1 }` を保存します。
3. アリスが切断。`alive[2]` が `false` になり、**`generation[2]` を 2 にインクリメントします**。
4. チャーリーが参加。スロット2に配置され、`Entity { index: 2, generation: 2 }` が渡されます。
5. ボブが `Entity { index: 2, generation: 1 }` に回復魔法をかけようとします。`is_live(alive, generation, ticket)` は現在の世代 `2` とチケットの世代 `1` が一致しないため `false` を返し、回復処理は行われません。

## 容量と世代の上限

追加と削除を実装するときは、次の規則を守ります。

- 再利用できる空きスロットがなければ、`Option` や用途に合う `Result` で伝えます。使用中のスロットを上書きしません。
- 削除前にもチケットを検査します。古いチケットで、新しい利用者の `alive` を消したり世代を進めたりしてはいけません。
- 世代カウンターをラップさせません。Align の整数加算はラップするので、`i64` を増やし続けると、いずれ古いチケットと一致します。最大世代に達したスロットは、最後の利用者を削除するときに再利用不可にします。`alive` とは別にその状態を記録し、追加時の候補から除きます。

たとえばスロットが1つなら、世代 `1` の利用者を削除した後は、世代 `2` として発行できます。世代 `1` のチケットは無効です。最大世代の利用者を削除した場合は再利用できるスロットがなくなるので、次の追加は満杯として失敗します。カウンターには上限があり、上限に達したスロットを再利用しないことが、古いチケットを拒否し続けるための方針です。

## プールで得られるもの

この構造には3つの利点があります。

1. **領域の再利用:** 参加・退出では、確保済みのスロットを使い回します。
2. **キャッシュ局所性:** 各フィールドが連続した列に並びます。全員に毒ダメージを与えるような一括更新は、`hp` の列を直接パイプラインで処理できます。
3. **古いチケットの検出:** スロットが使用中かと、その世代がチケットと一致するかを確認します。

固定容量のプールは、上限を先に決められ、データごとに寿命が異なる場合に使えます。再利用するスロットの利用者を、世代付きチケットで識別します。

# Align で高速な処理を書く

> 🌐 [English](../26-performance.md) · **日本語**

この章は、正しい結果を出すプログラムの実行時間やメモリ使用量を減らしたい人向けです。実際の処理を起点に、走査とメモリ確保の回数を数え、一つずつ変更して測ります。パイプライン、明示的な所有権、連続したメモリ配置は、コンパイラが最適化に使える情報になります。ただし、すべての処理がベクトル化されるわけでも、スレッドを増やせば速くなるわけでもありません。

## 比較に使える基準を作る

一度ビルドしてから、代表的な入力で実行ファイルを測定します。

```text
alignc build app.align --profile release --target-cpu baseline
./app
```

2行目がプログラムの実行です。この実行ファイルを計測・プロファイリングツールで測ります。`alignc run` を測ると、コンパイラ、キャッシュ、リンカの処理も含まれます。結果にはコンパイラのバージョン、プロファイル、CPU ターゲット、入力サイズ、測定したマシンを記録してください。特定の処理を調べるときは、起動、パース、計算、出力を分けて測り、全体の測定値も残します。

入力は実行時に読み込むか生成します。このガイドの小さな配列リテラルは動作を説明するためのもので、コンパイラが実行前に答えを計算できてしまいます。計測区間の後にチェックサムを表示するなど、計算結果を利用してください。同じ結果を出す実装を比較し、新旧の実行順を交互にして繰り返し測り、採用した統計値とばらつきを記録します。小さい入力、大きい入力、空の入力、偏りのある入力も、用途に応じて試します。あるサイズでの改善が、別のサイズでは悪化になることもあります。

実行順は `A,B` の次を `B,A` にして均等にします。毎回 A を先に実行すると、
B だけが温まった入力キャッシュや異なる CPU クロックの恩恵を受ける場合があります。
初回の遅延と準備後のスループットは分け、必要ならスレッドプールの初期化や
ファイルキャッシュの状態も区別します。同じ順序で反復を増やしても、この偏りは消えません。
タイマーで安定して測れないほど短いカーネルは、実行時入力と利用される結果を保ったまま
複数回をまとめて測り、呼び出し回数で割ります。

次回も同じ条件で比較できるよう、短い記録を残します。

```text
ソースのリビジョン、alignc のバージョン、OS/CPU、正確なビルドオプション
入力の識別情報・サイズ・分布、期待するチェックサムまたは浮動小数点の許容誤差
計測区間、初回か準備後か、標本数と実行順序
変更前後の実時間、中央値とばらつき、ns/要素またはバイト/秒
ピークメモリ、出力サイズ、測定した場合は確保・コピーの根拠
```

遅延とスループットには実経過時間を使います。並列化で実時間が減っても、
合計 CPU 時間は増えることがあります。同様に、常駐メモリのピーク、使用中のデータ量、
確保回数は別の指標です。領域を再利用しても全バイトをコピーする場合はあります。
まとめて「メモリ使用量」とせず、何を測ったかを明記します。

既定の `release` は O2、`fast` は O3 です。同じ処理で比較してください。`--target-cpu native` は現在のマシン向けなので、実行先と一致する場合に使います。移植性を保つ場合は `baseline`、実行先のマシンが決まっている場合は、そのマシンで利用できる LLVM CPU 名を指定します。比較する実装間ではターゲット設定を揃えます。

## 命令数の前に走査回数を数える

次の完全なプログラムを `energy.align` として保存します。

```align
fn positive_energy(xs: slice<i64>) -> i64 {
    return xs.where(fn x { x > 0 }).map(fn x { x * x }).sum()
}

fn main() -> i32 {
    xs := [1, -2, 3, 4]
    print(positive_energy(xs))    // 26
    return 0
}
```

絞り込み、乗算、合計が一つの走査になり、中間配列は作りません。`.sum()` の前に `.to_array()` を挟むと、選んだ値の二乗を保存する領域と、その配列を合計する2回目の走査が必要になります。後続の処理が配列を必要とする場合や、計算コストの高い変換結果を再利用する場合には、配列化が役立ちます。そのコストを意識して選びます。

チェッカーは、間に別の段階を挟まない `.to_array().sum()` に対して、
融合した合計を検討するよう警告します。警告は配列化した箇所を指し、名前を付けた
配列や再利用する配列には出しません。自動でコードを編集せず、実行時の割り当てが
最適化後にも残るとは保証しません。手動で変更するときは、意図した型と
浮動小数点の計算段階の境界を保ちます。

| 書き方 | 数える仕事と領域 |
| --- | --- |
| `xs.map(f).where(p).sum()` | 一つに融合した走査。中間コレクションなし。 |
| `xs.map(f).to_array()` | 一回の走査と結果の領域。 |
| `xs.map(f).map_into(dst)` | 既存領域へ書き込む。結果用の確保なし。 |
| `xs.sort()` | 所有されたソート結果を作り、作業領域も使うことがある。 |
| `xs.par_map(f)` | 所有された結果を作り、並列処理の準備とスケジューリングも行う。 |

これはコレクション操作のコストです。`f` や `p` の中の処理も、明示的なメモリ確保を含めて数えます。整数演算はオーバーフロー時にラップするため、高速化してもその結果を保つ必要があります。各操作の詳しい契約は[パイプライン](06-pipelines.md)を参照してください。

## 出力の形が一定なら領域を再利用する

`out` スライスを使うと、書き込み先を関数の契約に含められます。

```align
fn double_into(xs: slice<i64>, out dst: slice<i64>) {
    xs.map(fn x { x * 2 }).map_into(dst)
}

fn main() -> i32 {
    xs := [1, 2, 3, 4]
    mut ys := [0, 0, 0, 0]
    mut dst: slice<i64> := ys
    double_into(xs, dst)
    print(ys.sum())    // 20
    return 0
}
```

書き込み先には必要な長さがあり、入力と重ならないことが必要です。`map_into` が受け付けるのは長さを保つ map・射影の連鎖で、絞り込みを含むパイプラインは使えません。`xs` 自体をその場で更新する操作でもありません。状態を繰り返し更新するなら、2本のバッファで入力と出力の役割を交互に入れ替えられます。[ECS の例](22-building-a-system.md)では、フレームループ全体でこれを使っています。

arena はスコープの終了時に確保した領域をまとめて解放します。長いループを囲む arena では、各反復の確保がループ終了まで残ります。書き込み先を再利用するか、結果をバッチの外へ持ち出す必要がなければ、バッチごとに arena を設けます。結果が Move 型であるだけでは、arena に属する領域が独立した領域になるわけではありません。

出力に合った構築方法を選びます。

| 必要なもの | 操作と境界 |
| --- | --- |
| 個数が実行時に決まる型付き要素 | `array_builder<T>`。適切な上限が分かるなら `array_builder(capacity)` で予約する。容量は初期化済みの長さではない。 |
| 少しずつ組み立てるテキスト | `builder(capacity)` に書き込み、`to_string()` で完成させる。断片ごとの clone を避ける。 |
| 同じ値で初期化したバイト列 | `buffer.filled(length, value)`。`buffer(capacity)` の読み取り可能な領域は空から始まる。 |
| 末尾に同じ値のバイトを追加 | 可変 buffer の `append_filled(length, value)`。 |
| 既存のバイト領域の更新 | `slice<u8>.fill`、`copy_from`、またはエンディアンを明示した `set_*` / `fill_*`。領域を伸ばす操作ではない。 |
| 所有配列を短くする | `array.truncate(len)` は末尾の不要な要素をその場で Drop する。背後の容量を縮める操作ではない。 |
| レコード内の小さな固定長数値テーブル | `[T; N]` は要素をインラインに持つ。SIMD レジスタではなく、レコードをコピーすれば要素もコピーされる。 |

容量の予約は領域の拡張やコピーを減らせますが、書き込みやすべてのアロケータ呼び出しをなくすわけではありません。過剰な予約や大きなインラインレコードは、メモリ転送量を増やすことがあります。所有権と境界検査の規則は[メモリ](05-memory.md)と[文字列とテキスト](07-strings-and-text.md)を参照してください。

位置指定 I/O では `file.pread_into(buffer, destination_offset, length,
file_offset)` が予約済み領域へ再確保なしで読み込みます。書き込み開始位置は
初期化済みの長さ以下、要求範囲は容量以内である必要があります。成功時は実際に
書き込んだバイト数に応じて初期化済みの長さを伸ばせますが、未初期化の穴は作れません。
短い読み込みと EOF を扱い、報告されたバイトだけを処理します。ランダムな書き込み位置を
先に初期化する必要があるなら `buffer.filled` を使います。テキストビューの借用が
終わってからバッファを再充填してください。読み込みの境界が UTF-8 の文字や
レコードの境界と一致するとは限りません。

[上限付き CSV の例](../../../apps/csv/main.align)は、再利用する逐次読み込み領域と
失敗を扱える容量予約を使います。上限内の文書全体を蓄積してから UTF-8 検証と
デコードを行うため、領域をまたぐ文字や引用付きレコードを扱えます。入力全体と
デコード後の列の両方を予算に含めます。この例は文書全体に上限を設ける処理であり、
ストリーミング CSV デコーダーではありません。

## よく走査するフィールドを隣り合わせにする

多くの行の一部のフィールドを繰り返し読むなら、`soa<T>` や個別の列を使います。列の走査では、他のフィールドを毎回読み込まず、隣り合う値を読めます。行全体を使う処理が中心なら、行単位の配置を保ちます。変換コストも含めて判断してください。小さな処理のたびに `to_soa()` を呼ぶと、走査で節約する以上の時間がかかることがあります。対応する JSON の処理では、SoA へ直接デコードすれば独立した転置を省けます。

入力、出力、作業領域を含む処理対象をバイト数で見積もります。64 バイトの行から
8 バイトのフィールドだけを読む場合、全体走査が触れる行の領域は必要なフィールドの
8 倍です。これは配置の比較であり、8 倍速くなる保証ではありません。関連する
キャッシュ容量の前後でサイズを変え、絞り込みの通過率、キーの種類数と偏り、
整列状態も、仕事量が変わる場合には変えて測ります。配置を構築する時間は別に測り、
アプリケーションが実際に再利用する場合以外は、全体の時間にも含めます。

複数の列の同じ添字を組み合わせるには `zip` を使います。行の対応を保ち、組にした値を一緒に絞り込みます。同じキーで集計を繰り返すなら、`dict_encode` で文字列キーの ID を再利用できます。対応する入力・キーの形であれば、`group_by(...).agg(...)` で複数の集計を一回の走査にまとめられます。現在の制約と例は[データ指向設計](11-data-oriented.md)にあります。

ビューはデータ本体のコピーを避けますが、元の領域への寿命の依存を保ちます。所有者が生きている間は `str` やスライスを借り、独立した所有者が必要なときに clone します。バイトスライスの `.view_le()` は自然なアラインメントを満たすリトルエンディアンの数値データをコピーせずに参照でき、長さやアラインメントが合わなければ `None` を返します。数値の要素型は結果の期待型から推論するため、呼び出しに型引数は書きません。元の領域へのアクセス権限と寿命はそのままです。詰め込まれたデータ、アラインメントを満たさないデータ、逆のエンディアンのデータには、引き続きスカラーのバイト読み取り操作を使います。ビューを作っただけで、利用側の SIMD 化が保証されるわけではありません。

## 数値計算の意味を明示する

数値カーネルは、まず通常のスライスパイプラインで書きます。`vecN` の操作へ置き換える前に、生成コードを確認してください。明示的なベクトルでも、全レーンを読めること、余りの要素を処理すること、ターゲットに合う幅を選ぶことが必要です。マスクで範囲外のロードを安全にはできず、`select` は値を渡す両方の引数を評価します。[明示的 SIMD](12-simd.md)を参照してください。

浮動小数点の計算は、既定では順序を保ち、乗算と加減算を融合しません。`--profile fast` は fast-math を許可しません。アルゴリズムが丸めの違いを許容するなら、`float(reassoc) { xs.sum() }` で再結合を明示的に許可できます。`float(contract) { a * b + c }` は、その乗算と加算の組の融合を許可します。二つの許可は独立しており、併用もできます。名前付き関数やラムダの本体は毎回厳密な規則から始まるので、呼び出し側の許可はコールバック内の計算へ伝わりません。

再結合と融合では、丸め、ゼロの符号、NaN のペイロードが変わり得ます。アルゴリズムに根拠のある許容誤差を決め、通常の入力だけでなく例外的な値も検査します。計算の変形を許すことと、ベクトル命令や速度向上が得られることは別です。厳密な規則は[仕様](../../../draft.md#float-semantics)にあります。

## 逐次処理を測ってから並列化する

許可された Pure な関数 `f` に対して、`par_map(f)` は `map(f).to_array()` と同じ値を同じ順序で返します。出力が配列なら、この二つを比較します。最終結果が合計値だけなら `map(f).sum()` とも比較してください。対応する整数の `par_map(f).sum()` を直接消費する形では、中間配列全体を作らず、範囲ごとの部分和を使えます。対応するチャンク入力でも同様です。先に配列を束縛する、別のステージを挟む、浮動小数点を合計する、といった変更で選択が変わり得ます。`explain-opt` の `range-reduce`、`range-materialize`、`sequential-collect` は異なるコストを表します。

ワーカーの準備、スケジューリング、結果の配列化、メモリ帯域、要素ごとの仕事量が速さに影響します。小さい入力や軽い処理では、逐次の方が速いこともあります。`explain-opt` はコンパイラが範囲分割の実行方式と逐次へのフォールバックのどちらを選んだかを示しますが、範囲分割の方式でも、実行時に呼び出し元だけで処理する場合があります。特定の入力が実行時にどの経路を通ったかを示すものではありません。並列コールバックには純粋性とキャプチャの制約もあり、Move 値や region の確保権限はワーカーへ送れません。独立したタスクには `task_group` を使い、スコープ内で合流します。両方の使い方は[クロージャと並列処理](10-closures-and-parallelism.md)にあります。

コールバックがまとまった要素を処理するなら `chunks(k)` を使い、正のチャンク幅を
複数試します。チャンクごとの仕事が小さすぎるとスケジューリングの割合が増え、
チャンク数が少なすぎるとワーカーが余ります。仕事量に偏りがあれば、最も遅いチャンクが
全体を決めます。末尾は短い場合があります。浮動小数点のチャンクごとの合計をさらに
足すと、各チャンク内の演算が厳密でも、一回の厳密な sum とは計算のグループ分けが
変わります。数値結果も比較してください。`alignc -j` はコンパイルのワーカー数であり、
プログラム実行時の並列度を指定するものではありません。

## 知りたいことに対応するコードを調べる

最初の例では、関数を調査対象のルートとして残します。これにより、`main` のリテラル入力が定数化されてもカーネルを調べられます。

```text
alignc explain-opt energy.align --profile release --target-cpu baseline --export positive_energy --verbose
alignc emit-llvm energy.align --profile release --target-cpu baseline --export positive_energy --stage optimized --no-rt-lto
```

走査の融合、残ったランタイム呼び出し、境界検査、ベクトル演算、実体化された領域を見ます。境界検査が必要な場合もあるので、計測値を良くするために検証を取り除かないでください。現在のループ解析は特定の形を認識するため、同じ意味の手書きループでも同じ最適化を受けるとは限りません。IR のベクトル型は有用な証拠ですが、最終的な機械語のコストまでは決まりません。

`explain-opt` は、ランタイム LTO を無効にした単位ごとの選択と LLVM の最適化情報を報告します。ThinLTO で最終リンクした実行ファイルの報告ではありません。`main` を持たないファイルでは、そのファイル自身の `pub` 関数が調査のルートになり、`--export` を指定すると対象を絞れます。最終的な命令を知るには、ビルドしたバイナリをプラットフォームの逆アセンブラで調べ、同じ成果物をプロファイルします。

ランタイム LTO は `release` と `fast` では既に既定で有効です。単位をまたぐ `--thin-lto` は、その二つのプロファイルのリンクを伴うビルドで明示的に指定します。実行時間への効果とビルドコストを測ってください。代表的な学習用の処理があれば、計測に基づく PGO も選択肢ですが、現在は `--thin-lto` と併用できません。コマンドと制約は[ツールチェーンの章](16-toolchain.md)を参照してください。

## ビルド速度を別に測る

編集時の待ち時間は、コールドビルド、変更なしの再ビルド、代表的な一箇所の編集後の
再ビルドで比較します。ターゲットとプロファイルを揃え、`--cache-stats` でフロントエンドと
コード生成の再利用を確認します。キャッシュにヒットしてもリンクが必要な場合があります。
`build --watch` は更新の間もプロセス内の情報を保持するため、毎回コンパイラを
起動する場合とは分けて測ります。

```text
alignc build app.align --profile release --cache-stats -j 4
alignc build app.align --profile release --cache-stats -j 4
alignc build app.align --profile release --watch --cache-stats -j 4
```

最初のコマンドがコールドなのは、指定キャッシュにも配布物のフォールバックにも
再利用できる項目がない場合だけです。コールドビルドの実験には専用の `ALIGNC_CACHE`
ディレクトリを使い、利用するプロセスがすべて終了してから削除します。
`ALIGNC_CACHE=off` はキャッシュへの保存も省くため、キャッシュ無効の実験として
区別して記録します。Linux では、インストール済みの `ld.lld` でリンク時間を減らせる
場合があります。`ALIGNC_LINKER=lld` を指定すると、その存在が必須になります。
変わるのはリンク速度であり、生成するプログラムの最適化レベルではありません。
`-j` の値は実経過時間とピークメモリの両方で比較します。

## 観測結果から次に試すことを決める

| 観測したこと | 次に試すこと |
| --- | --- |
| 確保やコピーが大半を占める | 書き込み先の再利用、測定に基づく容量予約、arena の寿命短縮、借用ビューの維持。 |
| 同じ行を何度も走査する | 対応するステージの融合、集計の統合、意図して配列化した結果の再利用。 |
| 時間のかかる走査が少数のフィールドだけを読む | 列や SoA と比較する。作るコストも含める。 |
| 数値計算がスカラーのまま | 変形の可否と残った呼び出しを調べる。アルゴリズムが許す場合だけ、浮動小数点の明示的な許可を検討する。 |
| 並列版が遅い | 同等の逐次パイプラインと複数の入力サイズで比較する。結果の確保も含める。 |
| カーネルは速くなったがアプリは変わらない | パース、I/O、起動、出力を分けてプロファイルし、全体の測定値も残す。 |

リポジトリの[ベンチマーク手法](../../../bench/README.md#methodology-dont-skip)には、定数畳み込み、測定値のドリフト、誤解を招く差分計測の実例があります。測る前の練習には、[Little Aligner の最終章](../../little-aligner/ja/15-read-it-four-ways.md)で答えを予想し、データと寿命をたどり、仕事量を数えてみてください。

# Align の流儀

> 🌐 [English](../17-the-align-way.md) · **日本語**

前章までのイディオムを、コードを書くときやレビューするときのチェックリストとしてまとめます。

## まとめて変換する処理はパイプラインで書く

大量のデータの変換には `map`、`where`、`reduce` を使います。コンパイラはパイプラインの段階を融合し、ベクトル化できます。EOF までの読み込み、リトライ、収束計算などの逐次制御には、`break value` を伴う `loop` を使います。キーごとの一括集約には `group_by`、パーサや木のような再帰的な問題には再帰が向いています。ループで添字を増やしている場合は、パイプラインで直接表せないかを確認してみてください。

```align
total := xs.map(f).where(p).sum()
```

## エラーを伝播させるには `?` を使う

失敗しうる関数は `Result` を返します。呼び出し側で `?` を使うとエラーを伝播でき、`map_err` でエラー型を変換できます。理由を調べて処理する箇所では `match` を使います。理由が不要なら、`result else fallback` でエラーを捨てて代替値を返します。終了コードへの変換は `main() -> Result<(), Error>` に任せられます。

値がない場合は `Option`、操作が失敗する場合は `Result` を使い、関数の型でも区別します。

## 処理ごとにデータの寿命を決める

- ローカル値 → 特別な管理は不要です。
- 同じ処理フェーズで使う一時データ → `arena {}` を使い、外へ残すデータを `.clone()` します。
- テキストの組み立て → `builder` を使います。ループで `+` を使って結合しません。
- 別の所有者のデータ → ビュー（`str`、`slice`）を借用し、データのコピーを避けます。

まず、データをいつまで使うかを決めます。コンパイラがムーブやリージョン外への持ち出しを検査し、必要な後始末を挿入します。

## 大量のデータを SoA で配置する

多くの行のうち1〜2フィールドを繰り返し処理するなら、`to_soa()` で列ごとの配置に変換するか、JSON を直接 `soa<T>` にデコードします。文字列キーで集約を繰り返すなら、一度 `dict_encode` で整数化します。行全体を扱い、まとめて走査することが少ないデータには AoS が向いています。

## データ並列とタスクを使い分ける

要素ごとの計算が重い場合は `par_map` を検討します。ベクトル化された逐次パイプラインのほうが速い場合もあるので、計測してください。処理内容の異なる独立した仕事には `task_group` / `spawn` と `wait()?` を使います。並列クロージャには Pure が要求されます。純粋性は推論されるため、状態を変更したり I/O を行ったりするクロージャは拒否されます。

## コンパイラが解析しやすい形で書く

Align の制約は、連続したメモリ、エイリアスや null の不在、頻度の低いエラーパス、アリーナの寿命など、最適化に使える情報をコンパイラに与えます。パイプライン、`Result`、明示的なメモリ確保を使うと、追加の注釈なしにこの情報を保てます。これらのイディオムは最適化を助けますが、実際の速さは対象の処理で測定してください。

## ツールで確かめる

編集中は `alignc check`、コミット前には `alignc fmt --write` を使います。大きなコピー、不要なヒープ確保、情報を失うキャストの警告が出たら、原因を確認してください。パイプラインがベクトル化されたかは `alignc explain-opt` や `alignc emit-llvm` で調べ、実行時間はベンチマークで測ります。

## キーワードを手がかりにコードを読む

次の語は、確認したい操作を探す手がかりになります。

- メモリ確保：`arena`、`heap.new`、`builder`、`.clone()`、`.to_array()`
- 失敗：`Result`、`?`
- 変更：`mut`、`out`、`borrow mut`
- スレッド：`par_map`、`spawn`
- ネイティブリソース：`resource`
- 検査できない操作：`unsafe`、`raw`、`extern`

自分の API でも、こうした選択を呼び出し側から見えるようにすると、次の読者がコストや使用条件を理解しやすくなります。

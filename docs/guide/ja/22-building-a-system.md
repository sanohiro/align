# 22 — システムを組み立てる: ECS

> 🌐 [English](../22-building-a-system.md) · **日本語**

前章までに、データと処理の分離（19章）、長く使うデータのためのプール（20章）、状態機械（21章）を見てきました。

これらを組み合わせて、小さな Entity-Component-System（ECS）を作ります。ECS はデータ指向設計でよく使う構成の1つです。

## アーキテクチャ

OOP では、ゲームのエンティティはフィールドとメソッドを持つ「クラス」です。ECS では以下のようになります。
- **Entity（エンティティ）** は単なる ID（例えば `i64`）です。データは一切持ちません。
- **Component（コンポーネント）** は、並行した列に格納するデータです。ここではゲームループ全体を囲む `main` の arena で、配列を一度だけ確保します。`soa<T>` も同じ arena に置けます。どちらも1フレームで終わる arena には置きません。以下のシステムは、入力のスライスと `out` の書き込み先を受け取ります。宣言の断片は `main` 内に書きます。トップレベルの `:=` はコンパイル時定数の宣言になります。
- **System（システム）** は、コンポーネントの列をパイプラインで処理する関数です。

位置と速度を持つ、小さな1次元の世界をモデル化してみましょう。

## コンポーネント

`GameObject` クラスの代わりに列を定義します。エンティティを識別するのは、各列で共通の行番号です。

```align
// すべてのカラムの行 i = エンティティ i。
mut xs  := [0.0, 10.0, 20.0].to_array()   // 位置コンポーネント
vxs     := [1.0, 1.0, -1.0].to_array()    // 速度コンポーネント
```

実際のゲームなら、体力やスプライト ID などの列も加わります。一部のエンティティだけが持つコンポーネントには、`alive` と同様の `bool` 列と、20章の世代付きチケットを使います。フィールドごとに1列、エンティティごとに1行という構成は同じです。

## システム

System はコンポーネントに対して操作を行う関数です。どのクラスにも属していません。速度から次の位置を計算する Physics System（物理システム）を書いてみましょう。

Align では、システムはコンポーネントのカラムに対するパイプラインです。呼ぶたびに新しい配列を確保するのではなく、`map_into`（[The Little Aligner 05章](../../little-aligner/ja/05-chains.md)）で呼び出し元が所有する書き込み先に直接書き込みます：

```align
fn physics(xs: slice<f64>, vxs: slice<f64>, dt: f64, out next_xs: slice<f64>) {
    zip(xs, vxs).map(fn v { v.0 + v.1 * dt }).map_into(next_xs)
}
```

入力と書き込み先が明示されています。クロージャは純粋で、列は連続しているので、コンパイラは処理全体をベクトル化できるか解析できます。

3つのスライスは同じ長さで、`next_xs` はどちらの入力とも領域が重ならない必要があります。`physics(xs, vxs, dt, xs)` は `out` の契約に反します。次の2本のバッファは、列をまたぐエンティティのインデックスを保ちながら、読み込み先と書き込み先を分けるためのものです。

## ゲームループ

更新処理を `loop`（[The Little Aligner の11章](../../little-aligner/ja/11-do-it-until.md)）に入れます。ループを囲むアリーナで毎回メモリを確保すると、ループが終わるまで解放されません。そこで座標用のバッファを2本だけ確保し、役割を交互に入れ替えます。最初のフレームでは A から読んで B に書き、次は B から読んで A に書きます。

```align
fn main() -> i32 {
    arena {
        mut buf_a := [0.0, 10.0, 20.0].to_array()
        mut buf_b := [0.0, 0.0, 0.0].to_array()
        vxs := [1.0, 1.0, -1.0].to_array()

        mut frame := 0
        loop {
            if frame % 2 == 0 {
                physics(buf_a[..], vxs[..], 0.016, buf_b[..])
            } else {
                physics(buf_b[..], vxs[..], 0.016, buf_a[..])
            }
            // ...入力システム、描画システム: 同じカラム群に対する関数を続けて呼ぶ...
            frame = frame + 1
            if frame == 600 { break }
        }
        print(buf_a.len())
    }
    return 0
}
```

実際のゲームでは、経過時間を `std.time`、ウィンドウの状態を FFI（15章）で取得します。この例は固定の600フレームを実行します。アリーナは実行全体を通じて列を保持し、各システムをコードに書いた順に呼びます。`physics` は既存の書き込み先を使うので、フレーム数が増えても座標用のバッファは2本のままです。

## なぜこの構造がスケールするのか

1. **疎結合:** `physics` はスプライトを気にしません。描画システムは速度を気にしません。明日「体力（health）」カラムを追加しても、物理演算のコードには一切触れなくて済みます。
2. **予測可能性:** すべてが上から下へと流れます。他のメソッドを暗黙のうちに呼び出すような、隠された `Update()` メソッドは存在しません。
3. **性能:** 連続した列は、順次アクセスや SIMD に適しています。`alignc explain-opt` や `alignc emit-llvm` で、対象の環境で `physics` がベクトル化されるかを確認できます。

状態は配列に置き、各システムが変換を行います。システムを追加するときは、関数を1つ加え、ループ内のどこで呼ぶかを決めます。

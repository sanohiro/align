# 2. Do It Again

> 🌐 [English](../02-do-it-again.md) · **日本語**

**Q1.** ここに配列があります: `[1, 2, 3]`。各要素を2倍にして言ってみてください。

**A1.** `2, 4, 6`。いま頭の中で `map` をしましたね。

---

**Q2.** では Align で。`[1, 2, 3].map(fn x { x * 2 }).sum()` は何ですか？

**A2.** `12`。`map` が各要素を2倍にし — `[2, 4, 6]` — `sum` がそれらを足しました。

---

**Q3.** `fn x { x * 2 }` は何ですか？

**A3.** ラムダ（lambda）、つまり名前のない関数です。`fn` の後に引数と本体を書きます。引数の型は、入力する要素の型から推論されます。

---

**Q4.** 名前つきの関数を代わりに使えましたか？

**A4.** はい。使えます:

```align
fn double(x: i64) -> i64 = x * 2

[1, 2, 3].map(double).sum()
```

答えは同じ `12`。シグネチャさえ合えば、パイプラインのステージにはどんな関数でも渡せます。

---

**Q5.** `[1, 2, 3].map(fn x { x * x }).sum()` は何ですか？

**A5.** `14`。各要素を2乗した結果の和 `1 + 4 + 9` となります。

---

**Q6.** `[].map(fn x { x * x }).sum()` — 何もないものを `map` したら？

**A6.** このままではコンパイルできません。空の配列リテラルだけでは、要素の型が決まらないからです。`i64` の空のスライスなら、`map` する要素はなく、合計は `0` になります。

---

**Q7.** ラムダは、自分の外にある名前を使えますか？

```align
factor := 3
[1, 2, 3].map(fn x { x * factor }).sum()
```

**A7.** はい — 答えは `18` です。ラムダは `factor` を値で**キャプチャ**します。作られた瞬間にコピーを取るのです。

---

**Q8.** もし `factor` が `mut` で、`map` の *あと* に変わったら、`map` はそれを見ますか？

**A8.** 見ません。この `factor` は値でキャプチャされるので、ラムダを作った時点の値を使います。元の変数への、その後の変更は反映されません。

---

**Q9.** `[1, 2, 3].map(fn x { x * 2 })` — `.sum()` なしでは何ですか？

**A9.** コンパイルエラーです。パイプラインは、集計するか、配列などに実体化して終える必要があります。途中のパイプラインを値として保存することはできません。

---

**Q10.** では、2倍にした配列を本当に *取っておきたい* なら、どうしますか？

**A10.** その場合は明示的に指示します: `[1, 2, 3].map(fn x { x * 2 }).to_array()`。これで `[2, 4, 6]` が手に入り、メモリ確保（アロケーション）の存在がコード上で明確になります。

---

**Q11.** `[1, 2, 3].map(fn x { x * 2 }).map(fn x { x + 1 }).sum()` は何ですか？

**A11.** `15`。各要素に2つの `map` を順に適用すると、`3`、`5`、`7` になります。コンパイラはこの処理と `sum` を**1つのループに融合**します。

---

**Q12.** Q11 は途中でいくつ配列を作りましたか？

**A12.** ゼロです。各要素を変換してすぐに合計へ加えるので、`[3, 5, 7]` という中間配列は作りません。

---

**Q13.** 逐次 `map` の中で `print` してもよいですか？

```align
[1, 2].map(fn x {
    print(x)
    x * 2
}).sum()
```

**A13.** はい。`1`、`2` の順に表示し、答えは `6` です。逐次ステージは副作用を持てます。到達した各要素について、入力順・ステージ順にちょうど一度実行されます。

---

**Q14.** それでもパイプラインの中で表示するのが、たいてい悪い習慣なのはなぜ？

**A14.** 計算と表示が混ざり、最適化の選択肢も減るからです。また、同じ関数を `par_map` には渡せなくなります。ただし、逐次 `map` では副作用が許されることと、並列処理では許されないことを区別してください。

---

**Q15.** `map` が `par_map` になると、何が変わりますか？

**A15.** 要素を処理する順序が定まらないため、渡す関数は Pure でなければなりません。表示や外部状態の変更はできません。

---

**Q16.** 各要素から指を離さずに追ってください。

```align
[2, 4, 6]
    .map(fn x { x + 1 })
    .map(fn x { x * x })
    .to_array()
```

**A16.** `[9, 25, 49]`。一つの要素がパイプライン全体を通ります。`2 → 3 → 9`、次に `4 → 5 → 25`、そして `6 → 7 → 49`。

---

**Q17.** 2つの `map` を入れ替えると、同じ答え？

**A17.** いいえ。`[5, 17, 37]`。今度は `2 → 4 → 5` です。どちらも全要素を訪ねますが、関数の合成には順序があります。

---

**Q18.** すべての点数に10を足し、新しい点数を取っておく。終端は？

**A18.**

```align
scores.map(fn s { s + 10 }).to_array()
```

`.to_array()` です。変換後の点数を、配列にして保存します。

---

**Q19.** すべての点数に10を足し、合計だけを求める。終端は？

**A19.**

```align
scores.map(fn s { s + 10 }).sum()
```

`.sum()` です。合計だけが必要なので、変換後の点数を配列にする必要はありません。

---

**Q20.** `offset` は `7`。「すべての点を右へ7移動する」を書いてください。

**A20.**

```align
offset := 7
moved := points.map(fn x { x + offset }).to_array()
```

ラムダは外側の `offset` をキャプチャします。

---

**Q21.** 同じ変換を5か所で使います。何を変えるべき？

**A21.** 名前をつけます。

```align
fn move_right(x: i64) -> i64 = x + 7
```

そして `.map(move_right)` とします。一度だけの変換はラムダで、繰り返し使う変換は名前つき関数で書くと読みやすくなります。

---

> **第二の戒律**
>
> *各要素の変換には `map` を使え。結果を配列で残すなら、`to_array()` と書け。*

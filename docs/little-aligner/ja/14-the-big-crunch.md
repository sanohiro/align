# 14. The Big Crunch

> 🌐 [English](../14-the-big-crunch.md) · **日本語**

**Q1.** リクエストの記録を JSON 配列にした、10ギガバイトのログファイルがあります。`user_id` ごとのリクエスト数と、全体のうち `status == 200` のリクエスト数を数えてください。

**A1.** 読み込みとパースの後、条件で絞った件数と、グループごとの件数を求めます。

---

**Q2.** ファイル全体を、所有権を持つ文字列に読み込むとどうなりますか？

**A2.** デコードしたレコードを格納する前に、入力だけで10ギガバイトのバッファが必要です。そこへファイルの内容をコピーすることになります。

---

**Q3.** 代わりに、1件ずつデコードして処理できますか？

**A3.** はい。それなら全レコードを保持せずに済みます。今回は走査とグループ集計の両方で列を使いたいので、再利用できる形にデコードします。件数だけが必要な場合は、この章の後半でスキャナを試します。

---

**Q4.** では、10ギガバイトの入力をどう読み込みますか？

**A4.** 
```align
arena {
    view := fs.read_file_view("access.log")?
    ...
}
```
通常の空でないファイルなら、OS のメモリマップ（`mmap`）を使います。入力全体をコピーするバッファを先に作る必要はなく、アクセスしたページが OS のページキャッシュを通じて読み込まれます。ビューの寿命は、この arena の終わりまでです（8章）。ファイルを開く処理やテキストの検証は失敗し得るので、7章で習った `?` を使います。

---

**Q5.** 手元にあるのはテキストのビューです。ここから列を作るには？

**A5.** 同じ arena 内で、直接 SoA にデコードします。
```align
    logs: soa<Log> := json.decode(view)?
```

---

**Q6.** レコードに URL も含まれている場合、1件ごとに所有権を持つ文字列をヒープに確保するのですか？

**A6.** `str` フィールドなら、JSON のエスケープを含まない文字列は入力へのビューになります。エスケープを含む場合は、デコードした文字列を arena に格納します。どちらも URL ごとに独立した `string` を持つ必要はありませんが、文字列のコピーを省けるのはエスケープを含まない場合です。

---

**Q7.** `soa<Log>` 型の `logs` ができました。`status == 200` のリクエスト数を求めるには？

**A7.** 列は普通のスライスなので、3章で習った書き方が使えます。
```align
    ok := logs.status.where(fn s { s == 200 }).count()
```

---

**Q8.** この `where` は、条件に合う要素だけの配列を作りましたか？

**A8.** いいえ。`where` は `count` と融合して、列を1回走査します。状態の値を読み、条件に合う件数を数えるだけで、絞り込み後の配列は作りません。

---

**Q9.** では、`user_id` ごとのリクエスト数は？

**A9.** 10章のグループ集計を使います。
```align
    g := logs.group_by(.user_id).count()
```
`g.0` は重複のないユーザー ID、`g.1` は各ユーザーの件数です。同じ位置の要素同士が対応します。

---

**Q10.** ここまでを1つのプログラムにしてください。

**A10.**
```align
import std.fs
import core.json

Log { user_id: i64, status: i64 }

fn main() -> Result<(), Error> {
    arena {
        view := fs.read_file_view("access.log")?
        logs: soa<Log> := json.decode(view)?

        ok := logs.status.where(fn s { s == 200 }).count()
        g := logs.group_by(.user_id).count()

        print(ok)
        print(g.0.len())
    }
    return Ok(())
}
```

---

**Q11.** このプログラムは、どこでメモリを使っていますか？

**A11.** レコードごとに小さなオブジェクトを作る方式より、個別の確保や解放を減らせますが、メモリが不要になるわけではありません。メモリマップはアドレス空間を使い、アクセスしたページは物理メモリに読み込まれます。デコードした列には行数に比例する領域、グループ集計の途中の状態と結果にはユーザー数に比例する領域が必要です。省けたのは、入力をコピーするバッファ、レコードごとの個別オブジェクト、絞り込み後の中間配列です。

---

**Q12.** `arena` ブロックが終わるとどうなりますか？

**A12.** メモリマップが解除され、まとめて確保した領域も解放されます。ガベージコレクタが不要なレコードを探す必要はありません。寿命は最初から、このブロックまでと決まっています。

---

**Q13.** この書き方で省けた確保を、もう一度挙げてください。

**A13.** 入力全体のコピー、レコードごとの個別のヒープ確保、成功したリクエストだけを並べる配列です。デコードした列と、グループ集計の領域は必要です。

---

**Q14.** では*ゼロコピー*は、メモリも処理も不要という意味ですか？

**A14.** いいえ。ある処理の境目で、データのコピーを省いたという意味です。メモリマップは入力全体のコピーを省き、エスケープのない `str` は入力へのビューになります。エスケープを含む文字列は arena にデコードします。パースには計算が必要ですし、数値の列には格納先が必要で、OS によるページの読み込みもあります。どのコピーを省いたのかを確かめましょう。

---

**Q15.** 全体の `status == 200` の件数だけが必要で、グループ集計もデータの再利用もしない場合は？

**A15.** メモリマップしたテキストから、型を指定してレコードを1件ずつ読み出します。

```align
rows: json.scanner<Log> := json.scan(view)
ok := rows.status.where(fn s { s == 200 }).count()?
```

各レコードをデコードして順に集計するので、全件分の `soa<Log>` は作りません。読み進める途中で不正な入力が見つかる場合があるため、リデューサは `Result` を返します。

---

**Q16.** 最初のユーザーごとの `group_by` にも、スキャナを使わないのはなぜですか？

**A16.** スキャナで使えるのは、中間配列を作らずに融合して実行する集計です。`group_by`、`sort`、`to_array` を終端にはできません。列を再利用したり、グループごとの結果を作ったりするなら、全件分をまとめてデコードします。件数のように小さな結果だけが必要なら、スキャナで直接求められます。

---

**Q17.** 20ギガバイトの NDJSON から、件数を1つ求めます。ソートもグループ集計も再利用もしません。どの入力形式を使いますか？

**A17.** メモリマップしたビューを `json.scan` に渡し、融合したリデューサで集計します。必要な結果は件数1つなので、全件分のレコードを格納する領域は要りません。

---

**Q18.** 今度はレコードが JSON 配列で届き、20個のレポートで同じ5つのフィールドを繰り返し走査します。

**A18.** 必要なフィールドを宣言し、arena 内の `soa<T>` にデコードして、列を再利用します。確保とパースを一度行えば、その後の分析では列を繰り返し使えます。

---

**Q19.** 同じデータでも、小さなレコードを1件ずつ受け取り、すぐ次の処理へ渡す場合は？

**A19.** スキャナを選びます。SoA が向くのは、列を繰り返し処理する場合です。ファイルが大きいという理由だけで選ぶものではありません。

---

**Q20.** メモリマップした入力からデコードした `str` を、arena の外へ返したい。何が必要ですか？

**A20.** 所有権です。そのフィールドは、入力か、エスケープをデコードした arena 内の領域を借りています。外へ返す値だけを `.clone()` して所有するか、arena 内で使い終えるように呼び出し側を組み直します。

---

**Q21.** スキャナが900万行を処理したところで、不正な JSON を見つけました。途中までの件数を、正常な結果として返してもよいですか？

**A21.** いいえ。リデューサは `Result` を返し、`?` で呼び出し元に失敗を伝えます。1件ずつ処理しても、不正な入力の扱いは変わりません。途中までの結果が必要なら、その結果とエラーをどう返すか、インターフェースとして決める必要があります。

---

> **第十四の戒律**
>
> *入力をメモリマップし、用途に合わせてスキャナか再利用する列を選べ。各段階で必要な領域を確かめよ。*

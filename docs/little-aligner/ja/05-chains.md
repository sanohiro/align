# 5. Chains

> 🌐 [English](../05-chains.md) · **日本語**

**Q1.** これを左から右へ、声に出して読んでください:

```align
scores.map(fn s { s + 5 }).where(fn s { s >= 60 }).count()
```

**A1.** 「各点数に5を足し、60以上のものを残して数える」。式の左から右へ、同じ順序で読めます。

---

**Q2.** `scores := [55, 40, 90]` のとき、これは何を答えますか？

**A2.** `2`。5を足すと `[60, 45, 95]` になり、60以上の点数は2つです。

---

**Q3.** ステージの順序は問題になりますか？ 比べてください:

```align
xs.where(fn x { x > 0 }).map(fn x { x * 2 }).sum()
xs.map(fn x { x * 2 }).where(fn x { x > 0 }).sum()
```

**A3.** 2倍してもオーバーフローしないなら、答えは一致します。ただし、前者は先に絞り込むので、掛け算の回数が少なくて済みます。1章で見たように、整数がオーバーフローすると符号が変わることがあります。順序を変えてよいのは、入力に対する答えが変わらないときです。

---

**Q4.** ではこの2つは？

```align
xs.map(fn x { x - 10 }).where(fn x { x > 0 }).count()
xs.where(fn x { x > 0 }).map(fn x { x - 10 }).count()
```

**A4.** 答えが違います。`xs := [5, 15]` のとき、前者は10を引いてから正の数を残すので、個数は `1`。後者は正の数を残してから10を引くので、個数は `2` です。

---

**Q5.** なぜ C や Go のように `for` ループを書かないのですか？

**A5.** パイプラインなら、各要素への処理と必要な結果をそのまま書けます。添字や累積値を自分で管理する必要はありません。コンパイラはステージを融合し、処理の内容が許せばベクトル化できます。

---

**Q6.** `map` と `where` をつなぐと、ステージごとに中間配列ができるのですか？

**A6.** できません。`map` と `where` は終端処理と融合し、各要素を中間配列に保存せずに処理します。`sum` で終えるなら1つのループです。ただし、`scan`、`sort`、`to_array` は配列を作ります。そのあとに集計処理を続ければ、その配列をもう一度走査します。生成されたコードは `alignc emit-llvm yourfile.align` で確認できます。

---

**Q7.** では、長いパイプラインを複数行に分けて書いたら、何かコストがかかりますか？

```align
total := items
    .where(.active)
    .price
    .map(with_tax)
    .sum()
```

**A7.** かかりません。`.` で始まる行はパイプラインの続きとして扱われます。読みやすいところで改行してください。

---

**Q8.** パイプラインを途中で止めて、やりかけの仕事を持っておいてもいいですか？

```align
halfway := items.where(.active).price
```

**A8.** できません。`sum` や `count` で集計するか、`to_array` や `sort` で配列を作るか、`map_into` で既存のメモリ領域に書き込むところまで指定します。

---

**Q9.** では、絞り込んだ集合を2つの計算で *再利用* するにはどうしますか？

**A9.** 配列にして保存し、それぞれの計算に使います。

```align
active := items.where(.active).price.to_array()
print(active.sum())
print(active.max())
```

配列の確保が1回、その配列の集計が2回です。グループごとに複数の集計をまとめたい場合は、10章の `agg` を使えます。

---

**Q10.** ここで `chunks` は何をしますか？

```align
[1, 2, 3, 4, 5].chunks(2).map(fn c { c.sum() }).to_array()
```

**A10.** `[3, 7, 5]`。`[1, 2]`、`[3, 4]`、`[5]` の和です。`chunks(n)` は配列を最大 `n` 要素ずつのスライスに分けます。要素数が割り切れなければ、最後だけ短くなります。

---

**Q11.** すでにあるメモリ領域に結果を書くには、どうしますか？

```align
fn dbl(x: i64) -> i64 = x * 2

fn double_into(src: slice<i64>, out dst: slice<i64>) {
    src.map(dbl).map_into(dst)
}
```

**A11.** `map_into` を使います。新たなメモリ確保は行わず、結果をスライス `dst` に書き込みます。`dst` は `src` と同じ長さでなければならず、両者が重ならないことをコンパイラが確認します。バッファを繰り返し使いたい処理に向いています。

`out` は、書き込み先が呼び出し側から渡されたことを示します。この関数は、自分で確保した配列ではなく、引数の `dst` に書き込みます。`map_into` の宛先は、このように `out` 引数で受け取ります。

---

**Q12.** さて、習慣です。あなたはこれからループを書こうとしています。まず何を問いますか？

**A12.** 「各要素をどう変え、何を求めたいのか？」です。変換、絞り込み、集計として表せるなら、パイプラインで書けます。それで表せない繰り返しは11章の `loop` で扱います。

---

**Q13.** 融合するとき、`log` と `where` を入れ替えてもよいですか？

```align
xs.map(log).where(is_wanted).count()
xs.where(is_wanted).map(log).count()
```

**A13.** いいえ。1つ目はすべての入力で `log` を呼び、2つ目は条件に合った要素だけで呼びます。融合してもこの違いは保たれます。逐次処理の関数は、各要素について書かれたステージ順に実行されます。

---

**Q14.** 1つのループになっても、ステージの順序は意味を持つのですね？

**A14.** そのとおりです。1つのループになっても、各要素に適用する処理の順序は保たれます。

---

**Q15.** 「摂氏の気温から正のものを残し、0.5度を1とする単位に換算して、最大値を求める」を書いてください。

**A15.**

```align
temps.where(fn t { t > 0 }).map(fn t { t * 2 }).max()
```

正の値を `where` で残し、`map` で2倍して単位を換算し、`max` で最大値を求めます。

---

**Q16.** 変換後の値の個数も必要です。配列にして保存しますか？

**A16.** 入力の走査が安ければ、集計を2つ書くほうが単純かもしれません。変換に時間がかかる場合や、結果を何度も再利用する場合は、一度配列にして保存します。

```align
warm := temps.where(fn t { t > 0 }).map(fn t { t * 2 }).to_array()
hi := warm.max()
n := warm.count()
```

何を何回再利用するかで選びます。メモリ確保が必要なときは、明示して行います。

---

**Q17.** `[1, 2, 3, 4, 5, 6, 7]` を3要素ずつに分け、それぞれの合計を求めてください。

**A17.**

```align
[1, 2, 3, 4, 5, 6, 7]
    .chunks(3)
    .map(fn hand { hand.sum() })
    .to_array()
```

`[6, 15, 7]`。各まとまりは元の配列へのビューです。最後は1要素だけですが、要素を補ったりコピーしたりする必要はありません。

---

**Q18.** Q17 が `sum` ではなく `to_array` で終わるのはなぜ？

**A18.** 入力全体の合計ではなく、まとまりごとの合計を配列で返したいからです。

---

**Q19.** すでに書き込み先のバッファを持ち、2倍した値をそこへ入れたい。どの終端？

**A19.**

```align
fn scale_into(src: slice<i64>, out dst: slice<i64>) {
    src.map(fn x { x * 2 }).map_into(dst)
}
```

`to_array` は新しい配列を作り、`map_into` は呼び出し側から `out dst` として渡されたメモリ領域に書き込みます。同じ変換でも、結果を置く場所が異なります。

---

**Q20.** パイプラインが読みにくくなりました。半端なパイプラインに分割しますか？

**A20.** 関数に名前をつけるか、パイプラインを複数行で書きます。

```align
answer := xs
    .where(is_wanted)
    .map(normalize)
    .map(score)
    .sum()
```

変換の定義を関数に分けても、パイプラインは終端までつなげて書けます。

---

融合した集計と、`to_array()` で配列を作ってからもう一度走査する場合の違いは、ガイドの[パイプラインの章](../../guide/ja/06-pipelines.md)で図にしています。

> **第五の戒律**
>
> *パイプラインは左から右へ読め。答えが変わらない範囲で早めに絞り込み、必要な結果に合う終端を選べ。*

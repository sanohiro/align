# 6. One of Many

> 🌐 [English](../06-one-of-many.md) · **日本語**

**Q1.** 信号は赤か黄か緑です。同時に2つになることはありますか？

**A1.** ここでは、赤・黄・緑のどれか一つとして表します。こうした値に使うのが直和型（sum type）です。

```align
Light { Red, Yellow, Green }
```

---

**Q2.** 緑のものはどう作りますか？

**A2.** `Light.Green`。いつでもその型で修飾してください — 修飾なしの `Green` では、それがどの型のものか分からないからです。

---

**Q3.** いまどれを持っているかは、どう尋ねますか？

**A3.** `match` で、それぞれの場合の処理を書きます。

```align
fn go(l: Light) -> i64 = match l {
    Red    => 0,
    Yellow => 0,
    Green  => 1,
}
```

---

**Q4.** アームの中で、なぜ `Light.Red` ではなく `Red` なのですか？

**A4.** `match` では、調べる値の型がすでにわかっています。そのため、アームでは型名を省いてバリアント名を書けます。値を作る側では `Light.Green` のように型名も書きます。

---

**Q5.** `Green` のアームを消したら、どうなりますか？

**A5.** コンパイルエラーです。`match` がすべてのバリアントを網羅しなくなったからです。将来バリアントを追加したときも、ワイルドカードを使わずに列挙した `match` には、追加のアームが必要になります。

---

**Q6.** `Red` と `Yellow` は答えを共有します。アームを2つ書かねばなりませんか？

**A6.** `Red | Yellow => 0` とまとめられます。残りすべてを `_ => 0` で受けることもできますが、こちらは将来追加されるバリアントにも同じ処理を適用します。

---

**Q7.** バリアントは何かを運べますか？

```align
Shape { Circle(i64), Rect(i64, i64), Dot }
```

**A7.** はい — ペイロードを保持できます。`Shape.Circle(10)` は半径を保持した円です。`Shape.Dot` は何も保持しません。

---

**Q8.** 他の言語なら、クラスの継承と仮想メソッド `draw()` を使って様々な図形を扱うところです。なぜ Align では直和型と `match` を使うのですか？

**A8.** 直和型は、どんな図形があるかを列挙します。`match` は、それぞれの図形に対してこの操作が何をするかを列挙し、コンパイラが網羅性を確認します。バリアントとそのペイロードが決まっているので、コンパイラはデータの表現も把握できます。

---

**Q9.** ペイロードはどうやって取り出しますか？

**A9.** `match` のアームで変数名を割り当てます:

```align
fn area(s: Shape) -> i64 = match s {
    Circle(r)  => 3 * r * r,
    Rect(w, h) => w * h,
    Dot        => 0,
}
```

`area(Shape.Rect(3, 4))` は `12`。取り出した値を束縛する名前は、そのアームの中で使えます。`Rect` かもしれない値から、円の半径を直接取り出すことはできません。

---

**Q10.** `match` は文ですか、式ですか？

**A10.** 式です。Q9 の関数本体まるごとが式そのものです。変数に束縛したり、戻り値にしたり、引数として渡したりできます: `verdict := match s { ... }`。

---

**Q11.** 数に対して `match` してもよいですか？ `match n { 0 => ..., _ => ... }`

**A11.** できません。Align の `match` は直和型のバリアントを調べるためのものです。数値による場合分けには `if` を使います。

---

**Q12.** ペイロードには何を入れられますか？

**A12.** スカラーや構造体を入れられます。たとえば `Wrap(Point)` なら、`Wrap(p) => p.x + p.y` と取り出せます。`string` のような所有型も入れられます。その場合は直和型全体が Move になります。その値を破棄するときは、現在のバリアントが持つ値も解放します。

---

**Q13.** ページ取得の状態を表してください。読み込み中、取得完了（サイズを持つ）、失敗（エラーコードを持つ）のどれかです。

**A13.**

```align
Page { Loading, Ready(i64), Failed(i64) }

fn describe(p: Page) -> i64 = match p {
    Loading   => 0,
    Ready(n)  => n,
    Failed(c) => -c,
}
```

取得完了と失敗を同時に表す値や、読み込み中なのにサイズを持つ値は、この型では作れません。

---

**Q14.** もう一つ、直和型を使ってみましょう。

```align
Reading { Good(i64), Missing, Bad(i64) }
```

「`Good` の値を使い、それ以外は0にする」を書いてください。

**A14.**

```align
fn value_or_zero(r: Reading) -> i64 = match r {
    Good(n) => n,
    Missing => 0,
    Bad(_)  => 0,
}
```

2つの0は、答えが同じでも意味が違います。

---

**Q15.** 最後の2つのアームを `_ => 0` にできますか？

**A15.** できます。ただし、将来 `Stale(i64)` が増えたときの扱いが変わります。アームを列挙していれば追加の処理を書くよう求められますが、`_ => 0` なら新しいバリアントにも `0` を返します。

---

**Q16.** 測定値の配列から、`Good` に入っている値をすべて足してください。

**A16.**

```align
readings.map(value_or_zero).sum()
```

`match` で各要素のバリアントを調べ、パイプラインで配列全体を処理します。

---

**Q17.** `Bad` の測定値を数えるには？

**A17.**

```align
readings.where(fn r {
    match r {
        Good(_) => false,
        Missing => false,
        Bad(_)  => true,
    }
}).count()
```

`match` が述語の `bool` を作ります。

---

**Q18.** Q17 の `match` が `1` または `0` を返し、最後に `sum` してもよいですか？

**A18.** はい。

```align
readings.map(fn r {
    match r {
        Good(_) => 0,
        Missing => 0,
        Bad(_)  => 1,
    }
}).sum()
```

答えは同じです。条件に合う要素を数えるなら `where(...).count()`、各要素が返す数値を足すなら `map(...).sum()` と書くと、意図が伝わります。

---

**Q19.** `Reading` に `Stale(i64)` を足します。ここまでのどのコードに修正が必要ですか？

**A19.** バリアントを列挙した `match` です。`value_or_zero`、Q17 の述語、Q18 の関数に、新しい場合の処理を書く必要があります。

---

**Q20.** 直和型を作る前に、何を問うべき？

**A20.** 「同時に成り立たない状態はどれか？」です。測定値が `Good` と `Missing` の両方にはならないなら、別々のバリアントにします。両方が同時に成り立つ性質なら、構造体のフィールドが適しているかもしれません。

---

> **第六の戒律**
>
> *どれか一つになる値は、直和型で列挙せよ。`match` で場合を分け、網羅性はコンパイラに確かめさせよ。*

# 9. Turn It Sideways

> 🌐 [English](../09-turn-it-sideways.md) · **日本語**

**Q1.** 3人のユーザーを、1行に1人ずつ並べました。

```text
alice   30   true
bob     25   false
carol   41   true
```

全員の**年齢**を読んでください。目はどちらに動きますか？

**A1.** 列に沿って下へ。各行の名前とフラグは読み飛ばします。

---

**Q2.** では、表を*横倒し*にして、同じフィールドの値を1行に並べたら？

```text
name:   alice  bob  carol
age:    30     25   41
active: true   false true
```

**A2.** 横に1行読むだけです。メモリ上でも、この2通りの並べ方ができます。**AoS**（array of structs）は1件分のフィールドをまとめ、**SoA**（struct of arrays）は同じフィールドの値をまとめます。

---

**Q3.** なぜ並べ方が性能に関わるのですか？

**A3.** CPU はキャッシュライン単位でメモリを読み込みます。キャッシュラインが64バイト、年齢が `i64` なら、年齢の列は1ラインに8人分入ります。AoS では年齢だけを読みたくても、名前やフラグも一緒に読み込むことになります。連続した列は SIMD の読み込みにも向いています（ガイドの12章）。

---

**Q4.** 列を読むなら SoA がよいとして、AoS は何に使うのですか？

**A4.** 1件ずつ、レコード全体を扱う処理です。AoS はその1件のフィールドをまとめて置きます。SoA は、多数のレコードから特定のフィールドを繰り返し読むときに向いています。処理に合わせて選ぶものです。どちらの配置も、特定のプログラミング方式と結びついているわけではありません。

---

**Q5.** Align ではデータをどう横倒しにしますか？

**A5.** `arena` の中で `to_soa()` を呼びます。

```align
User { name: str, age: i64, active: bool }

arena {
    mut s := rows.to_soa()      // soa<User> — three columns now
    ...
}
```

型は `soa<User>`。扱うデータは引き続き `User` で、メモリ上の配置が変わります。

---

**Q6.** `s.age` は何ですか？

**A6.** 年齢の**列**です。型は普通の `slice<i64>` なので、ここまでに習った操作が使えます。`s.age.sum()`、`s.age.max()`、`s.age.map(...)...` などです。

---

**Q7.** 上の3人なら、`s.age.sum()` はいくつですか？

**A7.** `96`。メモリ上に連続して並ぶ年齢を合計しました。

---

**Q8.** `s.where(.active).age.sum()` は何ですか？

**A8.** `71`、つまり `30 + 41` です。bob は非アクティブなので除きます。この走査で読むのは、絞り込みに使う `active` と合計する `age` の2列です。名前の列は読みません。

---

**Q9.** alice のレコードを、1件丸ごと取り出すこともできますか？

**A9.** `u := s[0]` で、3つの列から `User` を1人分取り出せます。1列の読み込みと違い、3列から値を集める手間がかかります。列をまとめて読む利点と、行を取り出すコストの両方があります。

---

**Q10.** 1つの値を読み書きするには？

**A10.** `s[0].age` で1人分の年齢を読みます。`mut` な `soa` なら、`s[1].age = 26` で列の値を直接更新できます。

---

**Q11.** Q10 の更新後に、列の途中の範囲を切り出して合計するには？

**A11.** `s.age[1..3].sum()`。普通のスライスと同じように範囲を切り出せます。更新後なので `26 + 41 = 67` です。

---

**Q12.** SoA が向かないのは、どんな処理ですか？

**A12.** 設定を1件読む、リクエストを1件処理するなど、レコード全体をたまに扱う処理です。分かれているフィールドを、そのたびに集める必要があります。レコード単位で扱うなら AoS、大量のデータを列単位で走査するなら SoA が向いています。

---

**Q13.** データは JSON で届きます。まず行を作って、あとで横倒しにしなければなりませんか？

**A13.** いいえ。直接、列にデコードできます。

```align
s: soa<User> := json.decode(data)?
```

パーサは読みながら列を埋めるので、途中で行の配列を作りません。エスケープを含まない `str` フィールドは、入力テキストへのビューになります。エスケープを含む文字列はデコードして arena に格納するため、領域の確保が必要です。

---

**Q14.** ここまでの `soa` は、なぜすべて `arena` の中にあるのですか？

**A14.** ここで使った `to_soa` と `json.decode` は、列の領域を arena に確保します。そのスコープ内であれば何度でも分析に使え、スコープを抜けると列の領域が解放されます。

---

**Q15.** ここで覚えておくことは？

**A15.** *多数のレコードを列ごとに走査するなら、処理の前に SoA にする。* `to_soa()` で変換するか、`json.decode` で直接 `soa<T>` に読み込み、以降は列単位で処理します。

---

**Q16.** `rows.to_soa()` 自体には、コストがかからないのですか？

**A16.** 列の領域を確保し、全レコードを列ごとに並べ替えるコストがかかります。その後、列の走査を何度も行えば、変換のコストを回収できます。少数のレコードを一度だけ丸ごと処理するなら、変換の手間のほうが大きくなります。

---

**Q17.** では、処理のどの時点で配置を決めますか？

**A17.** 繰り返し処理を始める前です。JSON から読むなら、直接 `soa<T>` にデコードして行の中間配列を省けます。すでに AoS があるなら、その後の列ごとの走査で変換のコストを回収できるか考えます。毎回、機械的に SoA にするわけではありません。

---

**Q18.** AoS と SoA のどちらを選びますか？ 100万個の粒子の `x`、`y`、`velocity` だけを毎フレーム更新し、名前やメタデータは使いません。

**A18.** SoA。繰り返し実行するループでは、使わないフィールドをキャッシュに読み込まず、必要な列だけを走査できます。

---

**Q19.** では、12件の設定レコードを、普段は1件ずつ丸ごと読み込み、検証して表示する場合は？

**A19.** AoS。少数のレコードを丸ごと扱う処理では、列への変換で得られる利点はありません。

---

**Q20.** `Order` に `price`、`quantity`、`active` があります。有効な注文の総額を求めるには？

**A20.**

```align
orders
    .where(.active)
    .map(fn o { o.price * o.quantity })
    .sum()
```

`map(fn o { … })` には**行全体**が渡るので、ここでの `orders` は AoS の `array<Order>` です。この形の `map` は `soa<Order>` には使えません。全列から値を集めて行を組み立て直すことになるため、コンパイラが拒否します。SoA では `s.price` と `s.quantity` を取り出し、`zip`（13章）で組み合わせて集計します。`where(.field)` は SoA にも使えます。1列の条件で絞り込む操作なので、行全体を組み立てる必要がないからです（A8）。

---

**Q21.** 今度は `s` という `soa<Order>` を使います。なぜ `s.price.sum() * s.quantity.sum()` では総額にならないのですか？

**A21.** 合計する前に、注文ごとに単価と数量を掛ける必要があるからです。先頭の単価には先頭の数量が対応します。列ごとの配置になっても、値の対応関係は変わりません。

---

**Q22.** インデックス100から199までの行だけを分析するには？

**A22.** 集計の前に、列から必要な範囲を切り出します。

```align
s.price[100..200].sum()
```

終端の200は含まないので、100個の価格が対象です。

---

**Q23.** インデックスが見つかり、ある顧客のレコード全体が必要になりました。行を取り出すなら SoA を選んだのは失敗ですか？

**A23.** いいえ。`s[i]` で取り出せます。配置は、主に行う処理に合わせて選びます。列の走査を何度も効率よく行えるなら、ときどき行全体を取り出す手間は許容できます。

---

**Q24.** Q20 の計算を列で書いてみましょう。このプログラムは何を表示しますか？

```align
Order { price: i64, quantity: i64, active: bool }

fn main() -> i32 {
    arena {
        rows := [
            Order { price: 10, quantity: 2, active: true },
            Order { price: 100, quantity: 3, active: false },
            Order { price: 7, quantity: 4, active: true },
        ]
        s := rows.to_soa()
        prices := s.price
        quantities := s.quantity
        active := s.active
        total := zip(prices, quantities, active)
            .where(fn row { row.2 })
            .map(fn row { row.0 * row.1 })
            .sum()
        print(total)
    }
    return 0
}
```

**A24.** `48`、つまり `10 * 2 + 7 * 4` です。`zip` は同じインデックスの値を組にします。`.0` が価格、`.1` が数量、`.2` が有効かどうかです。タプルを1つずつ渡すので、タプルの配列は作りません。条件で残すかどうかは、組全体に対して判断します。

---

**Q25.** `zip` の前に、列を別々に絞り込んだり並べ替えたりしてもよいですか？

**A25.** 各列が同じ行を同じ順序で表す場合に限ります。長さが等しいだけでは、対応関係は保証されません。たとえば価格だけをソートすると、別の注文の数量と組になってしまいます。`zip` は長さが異なれば拒否し、短いほうに合わせて打ち切ることはありません。ただし、行の対応を保つのはプログラムを書く側の役目です。Q24 のように、先に関連する列を組にしてから、同じ条件で絞り込みます。

---

> **第九の戒律**
>
> *列を繰り返し走査するなら SoA を選べ。一度変換し、何度も使え。*

# 12. Do It Apart

> 🌐 [English](../12-do-it-apart.md) · **日本語**

**Q1.** 多数の値に同じ処理を行う方法は、もう知っています。

```align
ys := xs.map(expensive).to_array()
```

それぞれの値を同時に処理してもよいなら？

**A1.**

```align
ys := xs.par_map(expensive)
```

`par_map` と書くことで、並列に実行することを指定します。

---

**Q2.** `par_map` の後に `.to_array()` は必要ですか？

**A2.** いいえ。値として使うと、`par_map` 自体が所有権を持つ結果配列を返します。ただし、対応する整数の `par_map(...).sum()` を直接つなげた形は、結果全体の中間配列を作らず範囲ごとに集計できます。ソース上の意味は同じです。実際に確保する領域を数えるときは `explain-opt` で確認します。

---

**Q3.** Pure な関数なら、`map(f).to_array()` と `par_map(f)` の答えが違うことはありますか？

**A3.** いいえ。入力の各位置に対して、同じ値が同じ出力位置に入ります。並列化で変わるのは処理を実行する順番や割り当てで、プログラムの意味は変わりません。

---

**Q4.** `[3, 1, 2].par_map(fn x { x * x })` は？

**A4.** `[9, 1, 4]`。ワーカーが処理を終える順番にかかわらず、結果は入力順に並びます。完了順と、データの並び順は別です。

---

**Q5.** 渡した関数の中で、各値を表示してもよいですか？

**A5.** いいえ。どのワーカーが先に表示するかによって、出力順が変わってしまいます。`par_map` に渡す関数は Pure である必要があり、I/O や外部の状態の変更はできません。

---

**Q6.** `pure fn` と書く必要がありますか？

**A6.** いいえ。コンパイラが関数の処理内容から純粋性を推論します。呼び出し先で I/O、乱数生成、FFI、`unsafe`、外部の状態の変更を行っていれば、どの呼び出しが Impure の原因かを示せます。

---

**Q7.** 並列に実行するラムダは、外側の `factor` を使えますか？

```align
factor := 3
ys := xs.par_map(fn x { x * factor })
```

**A7.** はい。クロージャは `factor` の値をコピーして取り込みます。各タスクはその値を受け取るので、別のタスクに書き換えられる変数を共有しません。

---

**Q8.** `factor` が `mut` の変数で、後から変わる場合は？

**A8.** 第2章と同じく、クロージャは作られた時点の値を持ち続けます。外側の変数を変更しても、そのコピーは変わりません。

---

**Q9.** 100万個の整数に `f(x) = x + 1` を適用します。`par_map` を選びますか？

**A9.** まず逐次の `map` で書き、計測します。後続の処理と融合でき、ベクトル化できる場合もあり、ワーカーへの割り当ては不要です。ただし配列が必要なら、`map(...).to_array()` も `par_map(...)` も結果配列を作ります。合計だけなら、`map(...).sum()` はその配列も省けます。対応する整数の並列合計でも省ける場合がありますが（Q2）、スケジューリングのコストは残ります。同じ結果を求める処理同士で比べましょう。要素が多くても、1要素の計算が軽ければ並列化の手間が上回ります。

---

**Q10.** 独立した1000枚の画像に、それぞれ時間のかかる変換を行う場合は？

**A10.** `par_map` が候補になります。Pure な処理の計算量が十分にあれば、並列化の手間をかけても速くなる可能性があります。実際に計測して確かめましょう。

---

**Q11.** 6つの数を2つずつ、3つの組に分けて並列に合計します。

```align
fn chunk_sum(c: slice<i64>) -> i64 = c.sum()
```

式を完成させてください。

**A11.**

```align
total := [1, 2, 3, 4, 5, 6]
    .chunks(2)
    .par_map(chunk_sum)
    .sum()
```

各組の合計は `3`、`7`、`11`。最後にそれらを足して `21` です。

---

**Q12.** 数1つにつき1タスクにせず、チャンクにまとめるのはなぜですか？

**A12.** タスクの割り当てにかかる手間に対して、十分な量の計算をまとめたいからです。チャンクなら、メモリ上で近くにあるデータも一緒に処理できます。チャンクの大きさが、ワーカーに一度に任せる仕事量を決めます。

---

**Q13.** チャンクの処理が3番目、1番目、2番目の順に終わると、最後の合計は変わりますか？

**A13.** この整数の合計では変わりません。ラップする整数加算は、まとめ方を変えても同じ結果になり、コンパイラは Q2 の範囲ごとの直接集計を使える場合があります。浮動小数点の加算は異なります。チャンクごとの合計をさらに足すと、チャンクの結果が入力順に並んでいても、元の入力を厳密に一度合計する場合とは括弧の付き方が変わります。その書き換えを行う前に、数値精度の要件を確かめてください。

---

**Q14.** プロフィールの取得、モデルの読み込み、設定ファイルの読み込みという、異なる処理を並列に行います。これも `par_map` ですか？

**A14.** いいえ。同じ関数を各要素に適用する処理ではありません。少数の異なるタスクをまとめる `task_group` を使います。`par_map` に渡す関数とは異なり、`spawn` するタスクでは I/O を行えます。ただし、変更可能な状態の共有はできません。

---

**Q15.** 何を表示しますか？

```align
base := 100
task_group {
    a := spawn(fn { base + 5 })
    b := spawn(fn { base * 2 })
    wait()
    print(a.get() + b.get())
}
```

**A15.** `305`。2つのタスクはどちらが先に実行されてもかまいません。`wait()` で両方の完了を待ち、`.get()` で結果を読みます。

---

**Q16.** `task_group` を抜けた後も、タスクが動き続けることはありますか？

**A16.** いいえ。タスクの寿命はそのブロックまでです。完了を待たずにタスクを切り離したり、待ち忘れたままスコープを抜けたりはできません。

---

**Q17.** 1つのタスクが `Err` を返したら、`wait()?` は残りを待たずに抜けますか？

**A17.** いいえ。すべてのタスクの完了を待ってから、`?` でエラーを返します。複数のタスクが失敗した場合は、先に終了したものではなく、ソース上で先に `spawn` したタスクのエラーを選びます。後始末もエラーの選び方も、完了順には依存しません。

---

**Q18.** 選んでください。

- スライスの各要素に軽い算術処理を行う
- 多数の独立した要素に、同じ計算量の大きい Pure な関数を適用する
- 互いに独立した3つの異なる処理を行う

**A18.** 逐次のパイプライン、`par_map`、`task_group`。SIMD のレーンを使う計算、同じ処理の分担、異なるタスクの並行実行という、3つの使い分けです。

---

**Q19.** 並列のスケジューリングを明示的に要求する構文は？

**A19.** `par_map` と `spawn` です。並列化する境界を示しますが、要素やタスクごとに新しいスレッドを作る約束ではありません。実行時はワーカーを再利用し、構造化タスクを待つ呼び出し元も、キューにある仕事を実行できます。

---

**Q20.** チャンクの大きさは、どう決めますか？

**A20.** 代表的な入力で、複数の大きさを逐次版と比較します。小さすぎると計算より割り当ての手間が上回り、チャンク数が少なすぎると仕事のないワーカーができます。最後の短いチャンク、必要な結果領域の確保、最後の集計まで含めて比べます。ワーカーを増やしても、メモリ帯域が無限になるわけではありません。

---

**Q21.** タスクで所有する文字列を作り、グループが終わった後も使えますか？

**A21.** はい。

```align
message := task_group {
    task := spawn(fn { "ready".clone() })
    wait()
    task.get()
}
print(message)
```

`ready` と表示されます。タスクが所有する `string` を作り、完了を待った後、`get()` がその所有権を呼び出し元に移します。文字列はグループが終わっても使えます。単に `"ready"` を返すと借用ビューの `str` になるため、リテラルであってもタスクの結果にはできません。タスクの結果には、外部の借用に依存しないデータが必要です。対応する型の範囲は[並列処理のガイド](../../guide/ja/10-closures-and-parallelism.md)で説明しています。

---

**Q22.** `task.get()` を2回呼び、所有する文字列を2つ受け取れますか？

**A22.** いいえ。Move の結果を取り出すと、タスクのハンドルを消費します。文字列を2つ持ちたいなら、受け取った文字列を明示的に複製します。Q15 の `i64` の結果は Copy なので、正常に完了を待った後なら何度でも読めます。所有する結果を取り出さなければ、グループがすべてのタスクの完了を待ってから破棄します。第8章の規則は変わりません。所有する値の持ち主は1つです。

---

> **第十二の戒律**
>
> *計算量の大きい Pure な処理は `par_map`、異なる独立した処理は `task_group`。各タスクの寿命をスコープで区切り、失敗してもすべての完了を待て。*
